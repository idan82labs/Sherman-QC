## Degenerate component-span finding

The locked payload contains 15,609 zero-length component spans—43.58% of all
35,813 component records. These records are retained for census and rejection
funnels but are excluded deterministically from certificate recovery, A0 false
matching, and selected-component attribution because a point cannot satisfy a
finite line contract. None of the 31 valid certificates is zero-length.

The complete audit resolves their construction exactly:

| Zero-span structure | Count |
|---|---:|
| One physical parent, one mode, no cross-mode rung, one represented side | 10,821 |
| One physical parent, multiple modes, cross-mode rung, both represented sides | 4,788 |
| More than one physical support parent | 0 |

All 15,609 have `support_parent_count=1`. Component endpoints use the minimum
and maximum axial projections over unique physical support parents. With one
parent there is exactly one projection, so `lower == upper` mathematically
before coordinate rounding and before JSON serialization. The first class is a
single-side node. The second can contain a cross-mode edge and both normal-mode
sides, but every mode is still a child of the same spatial parent and supplies
no second physical position along the bend axis.

Therefore these zero spans are evidence of insufficient physical support in
the V2 primitive/component substrate, not an endpoint-formula defect. Expanding
a point into a line from its normal, voxel size, bin width, or a fixed minimum
length would invent a new representation and unsupported extent while being
mislabelled an endpoint-only repair. `DEGENERATE_SPAN_COUNTERFACTUAL` is removed
as a valid coequal next tranche.
