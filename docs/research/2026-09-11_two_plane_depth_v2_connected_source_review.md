## New profile binding and failure handling

The wrapper independently constructs the requested scheduler configuration and
calls the existing shared schedule binder. It then calls
`_validate_two_plane_context_configuration(context_report, "v2")` and requires
the context report to be COMPLETE before marking its profile bound. The fixed
expected version comes from the request, not from a returned schema claim.
The shared validator checks V2 schema, all 18 budget keys/exact integer values,
and every capacity key/type/value; it is not merely a per-pair quota check.

The new wrapper retains the real registration report and its attempted binding
error on failure, but clears auxiliary owned-role evidence so neither measurement
arm consumes an unbound registration. The existing registration oracle still
requires completed conditional contexts, not accepted global registration. The
measurement helper independently rechecks registration bytes, owned-role
fingerprints and immutable scan bytes before/after each arm.

The recorder catches ordinary call/oracle/safety failures, retains the declared
stage result and continues later stages. No failed scientific result can be
treated as a missing bend. Missing context makes later measurement stages fail
explicitly; it does not silently remove them from the denominator. Result
encoding failure retains only a bounded whole-discard receipt and fails the
packet. An unsuccessful registration oracle still vetoes the final aggregate.
Input-pin/custody assertions and resource termination may stop later dispatch;
the parent then records incomplete/unknown stages, not completed negatives.

These checks bind in-process reports and owned inputs. They are not independent
recomputation of a context's numerical geometry or proof against arbitrary Python
module mutation. The forthcoming source gate must qualify the corrected exact
engine bytes and representative deep handoff; this wrapper is not a substitute.

## Resource assessment

The proposed unchanged **6000 CPU / 6595 work / 6600 monitored parent seconds,
4 GiB sampled process-group RSS and 1 MiB output** is defensible for a new bounded
engineering attempt. It is not a measured successor throughput or worst-case
completion guarantee. No resource enlargement is justified by the machine's
available RAM, and no started cap may change.

The released composite POST reports U-R registration 210.721639 CPU seconds for
11 completed contexts and U-A 872.147698 for 48. A rough row-linear projection of
the latter to 650 rows is about 1,260 CPU seconds per 48-context L case. Increasing
U-R to its possible 48 contexts gives roughly 920 seconds. Alongside U-A, those
four rough registration terms total about 4,311 seconds, before changed prefilter,
context/cache/report and measurement work. The inherited planning subtotal near
4,800 seconds and 25% margin motivates 6,000; it is not a scaling theorem.

The corrected consumer now actually reaches up to 256 ordered matches, 1,024
signed families and 8,192 slots, unlike the immediate predecessor's 1.790749 CPU
seconds spent refusing before family generation. That rapid failure supplies no
throughput evidence. The old joint hypothesis, visits/cache/payload limits and
48 refined-start cap remain unchanged, but concentrated depth can change cache
reuse, finite-query cost, which groups are selected, and convergence behavior.
Both previously positive U cases can regress; all four positives remain required.

The old successful composite worker high-water RSS was 582,025,216 bytes. That
supports retaining, not guaranteeing, the 4 GiB guard for this small constructed
packet. More slots and full reports can allocate differently. The guard samples
one owned process group, forbids extra child processes and is not a hard allocator
cap. Worker RLIMIT supplies CPU enforcement; inherited supervision bounds its
monitored work/cleanup, not every synchronous setup/final filesystem operation.

Transport remains four planar results at 8 MiB, four registrations at 64 MiB and
eight measurements at 32 MiB: 544 MiB. Sixteen starts at 4,096 bytes add 65,536
bytes, totaling **570,490,880 bytes**. The 16 MiB role fingerprint and production
report/work limits are unchanged. A 64 MiB transport limit does not promise that
every permissible internal 96 MiB registration report fits; overflow is terminal
negative, without prefix rescue or retry. Inventory content reads occur only
after writer quiescence and are bounded to the 32 named regular no-follow files.
